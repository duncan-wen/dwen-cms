# Shipping

How a change reaches `main`.

**Branches, review, merge**: a spec's tickets ship together on one **integration branch** named `<feature-slug>`, off a freshly fetched `origin/main`. Build each ticket on its own branch `<feature-slug>-<NN>` (in a worktree when several are ready at once) and merge it back into the integration branch once `pnpm check` and `pnpm smoke` pass. After the first merge, open one draft PR with `gh pr create --draft --base main`; CI fails a PR whose base is anything else, since a PR merged into another branch never reaches `main`. When every ticket is done, run `/mattpocock-skills:code-review` against `origin/main` (it reviews against the spec as well as `CODING_STANDARDS.md`) and fix what it finds, then show the Owner the screenshots (see **Screenshots**), mark the PR ready, and once the Owner says OK, run `gh pr merge --auto --merge`: GitHub merges it the moment its checks pass, so nothing waits in the foreground. `main` is protected: GitHub refuses to merge a PR until its `check` job passes, and a PR whose `check` fails stays open with auto-merge pending. When `check` fails on a step the change didn't touch (a download, a runner outage), rerun it with `gh run rerun <run-id> --failed`. The `Vercel` check passing means the build, and with it the content check, succeeded. The Vercel preview is optional for the Owner; to check a path on it yourself, take the URL from the Vercel bot's comment (`gh pr view <N> --json comments --jq '.comments[].body' | grep -o 'https://[a-z0-9-]*\.vercel\.app'`) and send `x-vercel-protection-bypass: $VERCEL_AUTOMATION_BYPASS_SECRET` (from `.env.local`).

**One-off changes**: a change outside a spec (a retro, a one-off fix) gets its own branch off `origin/main`, e.g. `retro-<feature-slug>-<NN>`, and its own PR; run the built-in `/code-review` against `origin/main` (there is no spec to review against) and fix what it finds (a change to wording or content alone, with no code, skips it), then show the Owner the screenshots and merge once they say OK and its checks pass.

**Screenshots**: before ticking a box about how a page looks, or showing the Owner a visual change, run `pnpm shots <path>…` and read the screenshots. It builds `e2e/content`, shoots each path in light and dark at 1280px and 375px into `test-results/shots/`, crops each visible Illustration and Diagram on its own, writes `test-results/shots/index.html` with every shot on one page (the crops under their page's full shots), asks for reduced motion so an animation shows its finished frame, and fails if a page scrolls horizontally or a box other than a code block clips its content, sideways or downwards. `--content content` shoots the real content instead of `e2e/content`. A path ending `?open=<label>` (`'/posts/<slug>?open=所有頁面'`) is shot again with that fold opened first; a label no fold has presses the button named so instead (`?open=放大圖表` shoots a Diagram's Lightbox as the screen shows it). `/posts/typography-sample` holds every prose element. The Owner reviews from that page: give them `explorer.exe test-results/shots/index.html` to open it.

**After merging**: wait with `gh pr checks <N> --watch --fail-fast`, which returns as soon as a check fails, so a failure is seen at once rather than leaving auto-merge pending in silence; once `gh pr view <N> --json state` reads `MERGED`, run `pnpm prod:check /posts/<slug>` (the paths the change touched). It waits for `main`'s production deployment, then prints any error the production logs record against it and each path's status, and fails on either; tell the Owner about any error. The Hobby plan keeps under an hour of logs, and the MCP's `get_runtime_errors` answers 403, so this is the check. The Vercel MCP has no access to the `duncan-wens-projects` team; for other Vercel data (Web Analytics, deployment lists) call the logged-in CLI, `vercel api '<path>?projectId=dwen-cms&teamId=team_dUM4e6kZ7gTvxEVRfG8zGjpi'`.

**Preview env vars**: the Vercel CLI is logged in. Run `vercel link --yes --project dwen-cms` from the scratchpad, never the repo (linking writes `.vercel/` and edits `.gitignore`). A variable scoped with `--git-branch` needs that branch pushed first, and the push's own deployment starts before the variable exists, so `vercel redeploy` it once the variable is added.
