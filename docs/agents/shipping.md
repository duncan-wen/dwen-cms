# Shipping

How a change reaches `main`.

**Branches, review, merge**: a spec's tickets ship together on one **integration branch** named `<feature-slug>`, off a freshly fetched `origin/main`. Build each ticket on its own branch `<feature-slug>-<NN>` (in a worktree when several are ready at once), test-first with `/mattpocock-skills:tdd` so each test is seen red before the code that turns it green, and merge it back into the integration branch once `pnpm check` and `pnpm smoke` pass. A ticket the Owner needn't look at (nothing a Reader sees changes) may go to `main` in its own PR ahead of the rest, when the spec says so. After the first merge, open one draft PR with `gh pr create --draft --base main`; CI fails a PR whose base is anything else, since a PR merged into another branch never reaches `main`. When every ticket is done, run `/mattpocock-skills:code-review` against `origin/main` (it reviews against the spec as well as `CODING_STANDARDS.md`) and fix what it finds, then show the Owner the screenshots (see **Screenshots**), mark the PR ready, and once the Owner says OK, run `gh pr merge --auto --merge`: GitHub merges it once its checks pass, so nothing waits in the foreground. The merge lands a minute or so after `check` turns green, so a PR still open right after `gh pr checks --watch` returns is not stuck: wait for it with `pnpm prod:check` (**After merging**), never by merging it by hand. `main` is protected: GitHub refuses to merge a PR until its `check` job passes, and a PR whose `check` fails stays open with auto-merge pending. When `check` fails on a step the change didn't touch (a download, a runner outage), rerun it with `gh run rerun <run-id> --failed`. The `Vercel` check passing means the build, and with it the content check, succeeded. A push that only changes `.scratch/`, `docs/`, `.claude/` or the root's `*.md` since the branch's last deployment skips Vercel's build (`src/deploy/ignore-build.ts`), and so does its merge to `main`; a branch's first push always builds. A skipped build's `Vercel` check shows as skipped, and `check` is the one to wait for. The Vercel preview is optional for the Owner; to check a path on it yourself, take the URL from the Vercel bot's comment (`gh pr view <N> --json comments --jq '.comments[].body' | grep -o 'https://[a-z0-9-]*\.vercel\.app'`) and send `x-vercel-protection-bypass: $VERCEL_AUTOMATION_BYPASS_SECRET` (from `.env.local`). After changing an Animation, also shoot it mid-play with `?at=` at a few moments of its play (`pnpm shots '/posts/<slug>?at=2,5,9'`) and read those crops: the finished frame shows only where it ends.

**One-off changes**: a change outside a spec (a retro, a one-off fix) gets its own branch off `origin/main`, e.g. `retro-<feature-slug>-<NN>`, and its own PR; run the built-in `/code-review` against `origin/main` (there is no spec to review against) and fix what it finds (a change to wording or content alone, with no code, skips it), then show the Owner the screenshots and merge once they say OK and its checks pass.

**Which runs to repeat**: `pnpm smoke` and `pnpm shots` each build the site, a few minutes apiece. After a round of fixes, rerun the one the fix could change: `pnpm smoke` for code and tests, `pnpm shots` for anything a Reader sees. Run both, smoke first, on the last commit before the PR leaves draft.

**Screenshots**: before ticking a box about how a page looks, or showing the Owner a visual change, run `pnpm shots <path>…` and read the screenshots. It builds `e2e/content`, shoots each path in light and dark at 1280px and 375px into `test-results/shots/`, crops each visible Illustration, Diagram and Demo on its own, cuts a page taller than 1,600px into parts for an agent to read (`…-1280-part-<n>.png`, and a phone's parts four side by side as `…-375-sheet-<n>.png`), since the whole-page shot of a long page shrinks past reading, writes `test-results/shots/index.html` with every shot on one page (the crops under their page's full shots), asks for reduced motion so an animation shows its finished frame, and fails if a page scrolls horizontally or a box other than a code block clips its content, sideways or downwards (text clamped to an ellipsis with `line-clamp` may be cut short downwards). `--content content` shoots the real content instead of `e2e/content`. A path ending `?open=<label>` (`'/posts/<slug>?open=所有頁面'`) is shot again with that fold opened first; a label no fold has presses the button named so instead (`?open=放大圖表` shoots a Diagram's Lightbox as the screen shows it). A path ending `?scroll=<px>` (`'/posts/<slug>?scroll=1100'`) is shot as the window shows it after scrolling to that position, for what only shows once scrolled (a sticky header's line); it gets no parts, sheets or crops, so pass the plain path as well for those. To measure a page (an element's box, a computed value) rather than look at it, write a throwaway spec under `e2e/probe/` (gitignored, never run by smoke) and run `PROBE=1 pnpm exec playwright test` against the last `pnpm smoke` or `pnpm shots` build of `e2e/content`. `/posts/typography-sample` holds every prose element. The Owner reviews from that page: give them `explorer.exe test-results/shots/index.html` to open it.

**Next.js security notice**: when Next.js knows of a vulnerability in the installed version, the first `next build` stops with `SecurityFatalError`, and later builds print a warning that fails `pnpm build:check`. Rerun the command once to get past the stop; then upgrade `next` and `eslint-config-next` to the fixed release on their own `upgrade-next-<version>` branch and PR, a one-off change, and rebase the waiting change on it.

**After merging**: run `pnpm prod:check --pr <N> /posts/<slug>` (the paths the change touched). It watches the PR's checks and stops as soon as one fails, so a failure is seen at once rather than leaving auto-merge pending in silence; then it waits for the PR to merge and for `main`'s production deployment, and prints any error the production logs record against it and each path's status, and fails on either; tell the Owner about any error. The Hobby plan keeps under an hour of logs, and the MCP's `get_runtime_errors` answers 403, so this is the check. The Vercel MCP has no access to the `duncan-wens-projects` team; for other Vercel data (deployment lists) call the logged-in CLI, `vercel api '<path>?projectId=dwen-cms&teamId=team_dUM4e6kZ7gTvxEVRfG8zGjpi'`. Web Analytics has its own command and reading notes: `analytics.md`.

**Preview env vars**: the Vercel CLI is logged in. Run `vercel link --yes --project dwen-cms` from the scratchpad, never the repo (linking writes `.vercel/` and edits `.gitignore`). A variable scoped with `--git-branch` needs that branch pushed first, and the push's own deployment starts before the variable exists, so `vercel redeploy` it once the variable is added.
